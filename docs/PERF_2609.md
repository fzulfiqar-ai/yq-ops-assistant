# PERF_2609 — ops portal speed and the "Waking the server" screen (29-Sep-2026)

## What was actually wrong
The API was **not** asleep: Render showed one boot since the 28-Sep deploy and health checks answered
every 5 s throughout. The "Waking the server… ~30 seconds" screen came from `/me` stalling 41 s.

- **Shared HTTP/2 Supabase connection raced across threads.** postgrest 2.31 builds one
  `httpx.Client(http2=True)`; the API shares it across the whole anyio threadpool; httpcore 1.0.9
  allocates stream ids outside its lock. A page's burst of parallel calls broke it: PROTOCOL_ERROR
  GOAWAYs, Cloudflare HTML "400 Bad Request" ("JSON could not be generated"), 40 s stalls.
- **`/report/inventory` failed on every request**: a SQL alias `t` shadowed `run_readonly_query`'s
  own row alias. Never name an `exec_sql` output column `t` (tests/test_perf_transport.py guards it).
- **The portal's `/me` gate** ran several racing retry loops, called any slowness or 5xx "waking",
  and could replace the whole app mid-session.
- **Old Frankfurt service** kept waking for marketplace shoppers on an old cached bundle, spending
  the 750 h/month free budget that the always-on Singapore service needs (744 h in October).

## Deliberately not done
- `log_event` inserts in async upload routes: rare admin actions, one insert each; after the HTTP/2 fix
  a single insert blocks for milliseconds, and making audit writes fire-and-forget changes their meaning.
- Catalog context TTL (60 s): it carries stock availability for sold-out ordering; stays fresh.
- Persisting report data in the browser: the server's stale-while-revalidate already answers in ~0.2 s,
  and business figures would sit in localStorage on shared office PCs.
- Bundle trimming (motion, supabase-js): cached for a year after the first visit.
- Retrying JSON 5xx from Supabase's gateway: a 20 s platform blip is longer than any sane retry.
