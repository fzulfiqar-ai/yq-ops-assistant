What we are asking for

We run an internal reporting portal on top of Focus data. Today a staff member logs into Focus every morning, runs eight reports by hand, downloads them, and uploads the files to our system. We want that to happen automatically.

We are not asking to write anything back into Focus. Every dataset below is read-only. No document is created, edited, posted or cancelled by us — Focus stays the system of record and the only place transactions are entered.

The important thing to understand before quoting: our system already reads these exact reports and their exact columns. Whatever route we choose only has to deliver the same fields. It does not need to be clever.

Three routes, in the order we would prefer them

These are ranked by how quickly they deliver value against how much they cost to build. We are open to any of them — please quote whichever you can actually support.

ROUTE 1

Scheduled report delivery

Preferred first step

Focus runs the same eight reports on a schedule and drops the files somewhere we can collect them — SFTP, a watched folder, or an email inbox. Nothing about the report definitions changes.

We prefer this first because it needs no integration work on our side at all: our system already parses these files. If Focus can schedule and deliver them, we are done. It is also the easiest for your team to support, because nothing new is exposed.

Format XLS/XLSX or CSV, unchanged Delivery SFTP, folder, or email Our effort None
ROUTE 2

Read-only database access

A read-only login against the Focus database, limited to the sales, stock, receivables and pricing tables behind these reports. We would pull directly and never write.

This is the best long-term option for reporting: full history, no dependency on report layouts staying identical, and we can add a new metric without asking you for a new export. Please tell us if this conflicts with your support terms — if granting it voids support, say so and we will drop this route.

Permission SELECT only Scope Sales, stock, AR, pricing Access VPN or IP allowlist, fine
ROUTE 3

REST API

The Focus REST API, scoped to the entities listed below. This is the most future-proof option and the one we would choose if it covers the fields in the next section and supports fetching only what changed.

Our concern is coverage rather than capability: these are reporting figures — ageing buckets, profitability, price books — not plain transaction records. Please confirm the API returns these as computed values, or tell us which ones it cannot, before we commit.

Methods GET only Must support Filter by changed-since Needs Sandbox to test against

Three things that will bite us if unaddressed

These come from working with the current exports. Please confirm how each behaves in whichever route you quote.

1 · Salesman is arriving in the wrong field

In the Sales Day Book as currently configured, the salesman name comes through in the Warehouse Name column, not a salesman field. We have worked around it, but if the API or database exposes a proper salesman field, we would rather use that. Please confirm which field genuinely holds the salesman.

2 · Line totals are frequently empty

total_amount on sales lines is often blank, so revenue has to be reconstructed from the other columns. Please confirm whether the API or database returns a reliably populated line total, and state clearly whether each amount is VAT-inclusive or VAT-exclusive. Getting this wrong misstates revenue.

3 · We need to fetch only what changed

Pulling full history every day is wasteful and slow. For Route 2 or 3 we need to request records by date range or a modified-since timestamp. If the API can only return everything, say so up front — it changes which route makes sense.

Questions we need answered to decide

Please answer against whichever route you recommend. Commercial answers matter as much as technical ones.

  1. Which routes can you actually support?Of the three above, which are available on our licence and version — and which do you recommend?
  2. What is the cost, and what shape is it?One-time setup, annual licence, per-module, or per-call. Include anything that changes at renewal.
  3. Is it read-only, and can you guarantee that?We want write access explicitly excluded, not merely unused.
  4. How do we authenticate?API key, OAuth, or database credentials — and how are they rotated if compromised?
  5. Can we filter by date or changed-since?See point 3 above. This is close to a deal-breaker for the API route.
  6. Are there rate limits or page sizes?And what happens when we hit them.
  7. How far back can we pull?We want a one-time backfill of history, not just from go-live.
  8. Is there a test environment?We will not test integrations against live accounting data.
  9. Does the API return computed reporting figures?Specifically ageing buckets, profitability and price books — or only raw transactions we would have to recompute?
  10. What happens on a Focus upgrade?Who is responsible if a version change breaks the integration, and what notice do we get?
  11. How long to deliver?From order to working access, per route.
